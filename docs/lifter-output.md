# What the lifter emits

This page describes the code a guest instruction becomes. Read it when you need to know why a lifted function looks
the way it does, or what behavior the host can rely on. For the overview, see [The lifter](lifter.md). To see the
output for one function, run `nx2/lift2/dump.py` ([Build and iterate](lifter-build.md#inspect-a-function)).

## Functions, registers and the context

- Every guest function becomes `void f_<address>(ptr %ctx)`. That symbol is what the function table, the patches,
  the host and every call use. `%ctx` is the thread's `GuestContext` (`a64.h`, generated by `nx2/rtgen.py`): `x0` to
  `x30`, SP, the NZCV flags, and `v0` to `v31`.
- Inside a function, guest registers are SSA values. The entry block loads the registers the function reads before it
  writes them.
- Register writes are stored to the context where they happen, and LLVM removes a store that a later one overwrites
  before anything can read the context. Stores that no reader can read are not emitted at all: the lifter knows what
  each callee reads from its call-boundary record.
- After a call, registers are loaded from the context again, except the callee-saved `x19`-`x29` and SP across a call
  to a callee with a full summary. Those stay SSA values.
- A function with an MSR FPCR is emitted `strictfp`.
- Flags are not written through. They are stored only before an SVC and at exits that leave the function for other
  code (a tail call or an indirect jump). A return stores no flags: the AAPCS64 leaves them undefined there.

A context read from outside the thread (the crash handler, the stall dump) can show an older value for a register
whose store was omitted. The registers that an indirect call, an SVC or a call into the host reads are always current.

## Memory and ordering

A guest address `a` is host address `0x1000_0000_0000 + a`: one constant per function, folded into addressing, with
no bounds checks. The guest window is 2^39 bytes. Plain loads and stores are plain LLVM accesses with `align 1`. A
guest store is one host store; nothing records which pages were written.

The ordering follows x86-TSO:

| Guest | Emitted | x86 |
|---|---|---|
| LDR, STR | plain | `mov` |
| LDAR, LDAPR | `load atomic acquire` | `mov` |
| STLR | `store atomic seq_cst` | `xchg` |
| DMB or DSB, full kinds | `fence seq_cst` | `lock or` |
| DMB or DSB, load-only or store-only kinds | `fence acq_rel` | nothing (compiler barrier) |
| ISB | nothing | |
| LSE atomics (LDADD, SWP, and others), any ordering | `atomicrmw seq_cst` | `lock`-prefixed |
| CAS, CASP | `cmpxchg seq_cst` (CASP on i128) | `lock cmpxchg`, `lock cmpxchg16b` |
| LDXR, STXR and the pair forms | calls of the runtime's exclusive monitor | call |

The game uses the exclusives a handful of times against tens of thousands of LSE atomics, so their runtime calls cost
nothing measurable.

## Loops

Every cycle of a function's control-flow graph gets a *cycle barrier*: an empty inline-assembly statement that LLVM
treats as reading and writing all memory. It emits no instruction. Its effect is that a guest load inside a loop is
done on every iteration, so a spin-wait on a flag another thread sets keeps working.

YIELD and WFE become `pause`. The lifted code contains no polls: every guest thread runs freely on its own host
thread, and nothing depends on lifted code calling into the host regularly.

## Calls and returns

- **BL** sets `x30` and calls `f_<callee>`. If the summaries prove the callee never returns, a trap follows the call,
  so a wrong summary stops the game instead of running on.
- **B to another function** is a `musttail` call. All functions share one prototype, so every tail branch is a
  guaranteed tail call.
- **RET** is `ret void`.
- **PLT stubs** are resolved: a call of a stub calls its target.
- **setjmp callers** are called through a host stub that saves a host `setjmp`. A guest `longjmp` returns there and
  resumes the caller at the setjmp return address (`host/hos_setjmp.c`).
- **Calls of host code** follow the host's declarations: a replaced function keeps `x19`-`x29` and SP unless its
  declaration says `clobbers(...)`. See [Write a patch](patches.md).

## Indirect calls and jumps

Code pointers are host function pointers. The lifter translates them where they originate (`nx2/lift2/code_ptrs.py`):

- Every relocated slot of the image that holds a function's address is listed at lift time, and the host writes the
  function's host pointer into it right after loading `image.bin` (`host/code_ptrs.c`).
- Where the code forms a function's address with `ADR` or `ADRP`+`ADD`, the lifter emits the address of `f_<entry>`.
  The build stops if the number of translated sites differs from the census, or if code forms an entry's address any
  other way.
- Host functions handed to the game are host pointers too.

A BLR tests whether the target's high 32 bits are set. If they are, it calls the target directly. Otherwise it takes
the guest-address path: the runtime looks the address up in the function table and counts it. The host logs
`code pointers: N sites and M calls took the guest-address path` regularly; in a normal run both are 0. A guest load
of a host code pointer as data faults, because host pointers lie outside the guest window.

Two places in the game look at a code pointer's value rather than calling it:

- `__nnmusl_init_dso` checks that `nnMain` lies inside its module. A row hands it `nnMain`'s guest address.
- A gRPC channel-argument compare (`net_grpc_authority_table_arg_cmp`) orders arguments by function pointer. With host
  pointers that order differs from the guest's and between runs; nothing observes it, so it is left as it is.

## Jump tables

A BR through a jump table that discovery can prove becomes a dense `switch` on the loaded index. Tables discovery
cannot prove switch on the target's offset, which LLVM lowers to compare chains when the targets are spread out. An
index out of range takes the indirect-jump path.

## FP and NEON

FP arithmetic is native LLVM FP and is correctly rounded, so it equals ARM's in every rounding mode. The emitter
writes no `contract` flags and the build passes `-ffp-contract=off`, so nothing the guest kept separate is fused.

The host's MXCSR follows the guest's FPCR (`host/hos_fp.c`): FZ sets DAZ and FTZ, RMode sets the rounding control, and
all exceptions stay masked. The game sets FZ on its main thread, and results differ without it.

Where x86 differs from ARM, the emitter uses an exact replacement: `llvm.minimum` and `llvm.maximum` for FMIN and
FMAX, `llvm.minimumnum` and `llvm.maximumnum` for FMINNM and FMAXNM, saturating conversions for FCVTZS and its
relatives, ARM's estimate algorithm bit for bit for FRECPE and FRSQRTE, AES-NI and PCLMUL for the crypto forms, and
scalar code for SHA, CRC32 and the saturating shifts by register.

The tests (`tests/test_lift2_fp.py`, `nx2/test_lift2_leaf.py`) accept exactly these deviations from ARM and fail on
anything else:

| Class | What differs |
|---|---|
| `nan` | A NaN result's sign or payload. FPCR.DN is not modeled. `LIFT2_DEFAULT_NAN=1` at lift time gives ARM's default NaN for a NaN made from non-NaN operands. |
| `fz-boundary` | Under FZ, a result of the smallest normal magnitude: ARM detects tininess before rounding, x86 after. |
| `fz-minmax` | Under FZ, FMIN, FMAX and their relatives return a subnormal operand unflushed. |
| `snan-minmax` | FMINNM and FMAXNM treat a signaling NaN operand as quiet. |
| FPSR | MRS FPSR sees MXCSR's sticky bits, which also record operations the guest never did. |
| FRSQRTS | The halving is a separate multiply, which differs for results below 2^-125 (single precision). |

Half-precision FZ16 and AHP are not supported.

## System calls, traps and system registers

- **SVC** stores the flags, calls `a64_svc`, and reloads every register.
- **UDF, BRK, HLT** and words that are not code call `a64_trap`.
- **TPIDR_EL0** and **TPIDRRO_EL0** read and write the context. **CNTPCT_EL0** reads the host's counter, scaled to
  31.25 MHz.

## Fibers and C++ exceptions

- The SDK's fiber functions are replaced by the host (`host/hos_thread.c`): a guest fiber is a host fiber with its own
  guest context. The SDK's fiber assembly never runs.
- A C++ throw stops the game with the exception's type and the caller's address (`host/cxx_throw.c`). Unwinding
  through lifted frames cannot work, because lifted frames do not keep the return addresses an unwinder needs. The
  game throws only on error paths, and normal play throws nothing.
